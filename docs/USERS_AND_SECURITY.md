# Users, roles and security

The page **Security** (group Account) uses the single login of EH3D-SERVER (`/api/v1/auth/...`, `docs/AUTH.md` of that repository). Code: `src/pages/SecurityPage.tsx`, `src/services/authsvc.ts`, `src/services/permissions.ts`.

* **Session:** who the login is, its application, scopes, last use and expiry; renew it or sign out everywhere (people only; a token of a program has no login).
* **Open sessions:** the caller's, or everybody's for an administrator; closing one asks twice. The id of a session is not a token.
* **What each role may do:** a table that comes from the same rules the pages use.
* **Policy of the server** (administrator): every switch with its value and whether it is as strict as recommended, the ones that deserve a look first. No secret is ever in it. The switches the server lets change while it runs (`editable`: `url_token`, `audit_denials`, `design_run`, `network_open`, `update_allow_unsigned` and the limits of the logins and of the passwords) have a button, or a number to type and Save; when the server answers that the new value is looser than recommended (`409 weak_confirm_required`) the page asks again and sends the change with `confirm_weak`. The other switches are changed in `server.cfg` and the server is started again. `network_open` (the server listens on every address of the computer and not only on this computer, which is its default) is read when the server starts, so the table says next to it that it takes effect when the server restarts (`restart_required` of the policy). `update_allow_unsigned` lets the update helper install a release that has no signature when its hash is right; by default a signature of an allowed signer is required. Both are looser than recommended when on, so they ask twice.
* **The switches the server brings off:** `mdns_announce`, `compat_api`, `compat_write` and `slice_enabled` are off by default and each row says what it does; turning one on is looser than recommended, so the server asks for `confirm_weak` and the page asks the person again before it sends it. `compat_write` lets the routes of Moonraker and OctoPrint write, and even then nothing starts by itself.
* **Keeping the logins across a restart:** `persist_sessions` has a text of its own in the table and, when the server lists it as editable, a button; turn it on before an update of the server so that the restart does not end the logins. If the login ends anyway, the page of the updates asks for the name and the password again in a box of its own and goes on following the update where it was, showing the last known steps until the answer of the server is back. The password is only in the form while the request goes and is never kept.
* **All the settings of the server:** the page **Server** (group Configure) draws every setting and switch of the server from its contract (`GET /api/v1/settings/contract`, document `eh3d.settings.contract/1`; `docs/CLIENT_SYNC.md` of EH3D-SERVER): the groups in the order of the contract, and for each key its label, help and warning in the language of the person (the eight languages of the contract; the other languages of Studio read the English text, and `pt-br` and `fr-ca` read their main language), the value in force, the default with a button to restore it, whether a change applies at once or needs a restart, and the control of its type (a switch, a number with its range and unit, a text, a list or a choice). An administrator changes the keys the contract says the API writes (the ones of `PUT /api/v1/auth/policy`); the number is checked against its range before it is sent, a change with a risk to the security, the exposure, a machine or the data is asked first with its warning, and a value looser than recommended is asked again when the server says so (`confirm_weak`). The keys that are set in `server.cfg` show their value and say so, with no control. A secret never shows its value and is never written. A person who is not an administrator sees the same page read-only. When the live contract cannot be read (a role without the scope, a server without the route, an answer Studio does not understand) the page shows the copy that Studio keeps (`src/data/settings-contract.json`, checked against the file of the server by `tools/sync_settings_contract.py`) read-only, says why, and shows no value in force. A login that is not an administrator reads instead the light, read-only view of the values in force (`GET /api/v1/settings/values`, any role, a few kilobytes, `eh3d.settings.values/1`): Studio sends the `ETag` of the last answer in `If-None-Match` and keeps the page on a `304`, shows the values with the texts of its own copy, keeps no value for a secret or a path of the computer, refuses an answer over 16 KiB or malformed, and warns when the `contract_hash` of the server is not the hash of its copy (`src/services/contracthash.ts`). Nothing can be changed from the light view. A key that the server reports and that neither contract describes is shown with a generic read-only line, so nothing the server holds is hidden. The table of the policy above stays as the short view of the switches that deserve a look and links to this page. Code: `src/components/ServerSettings.tsx`, `src/services/settingscontract.ts`.
* **Audit** (administrator): the lines of `GET /api/v1/audit` with the filters by person and by event, the newest first, with the other fields of each line written as `key=value`. When the audit file is switched off on the server the page says so.
* **Keys and TLS fingerprint** (administrator): the tokens of the programs by identifier, name, role, creation, last use and expiry (never their secret), and the SHA-256 fingerprint of the certificate that `tls_cert_file` names in `server.cfg` when the server has one.
* **Where the login token is kept** (`src/tokenstore.ts`): in `sessionStorage` of the tab, so it is gone when the tab or the browser is closed and another tab does not see it. At the sign-in the box **Remember me on this computer** (off by default, with a warning about shared computers) keeps it in `localStorage` instead, so the next visit needs no password; the token is then in one store only, never in both. Signing out, or a refusal because the login ended, removes it from both. A token that an earlier version left in `localStorage` is still read, and is kept as remembered until the person signs out. A browser that keeps nothing is not an error: the login lasts until the page is closed.
* Users and tokens stay in the page Users and tokens.

## Sign-in

Studio signs in with `POST /api/v1/auth/login` and `app: "studio"`, so the login is listed with its application and the audit says where it came from.
